# deserialization — 不安全反序列化定义

## 1. 漏洞定义是什么

**不安全反序列化**：应用程序将 **攻击者可控的序列化数据** 还原为对象/结构，并在还原或后续使用中触发 **非预期代码执行或逻辑**。

常见格式：Java 原生序列化、PHP `unserialize`、Python `pickle`、YAML `load`、.NET `BinaryFormatter`、带类型信息的 JSON 等。

**成立必要条件**：

1. 反序列化入口处理不可信数据  
2. 存在危险类型解析/gadget/魔术方法副作用  
3. 未使用安全替代（白名单类型、JSON 无类型、签名封装）  

---

## 2. 严重（Critical）

| # | 判定条件 |
|---|----------|
| C1 | 未认证或普通用户可控 payload → **RCE** |
| C2 | 反序列化导致 **任意文件写/JNDI 注入** 等沦陷级后果 |
| C3 | 可伪造 **管理员会话对象** 实现身份平面沦陷 |

---

## 3. 高危（High）

| # | 判定条件 |
|---|----------|
| H1 | 仅高权限角色可触发，但角色易得或管理面暴露，可 RCE |
| H2 | 未直接 RCE，但可 **破坏完整性**（改余额、改角色对象字段）影响重大 |
| H3 | 已知 gadget 链与入口匹配，利用条件在目标环境 **高度可能**，差稳定 PoC |

---

## 4. 中危（Medium）

| # | 判定条件 |
|---|----------|
| M1 | 反序列化不可信数据，但类型白名单较严，**仅 DoS** 或有限逻辑影响 |
| M2 | 入口存在但 **无可用 gadget**（旧库已移除）且不能证明其它危害 |
| M3 | 仅内网且需已持有其它高权限凭证才能投递 payload |

---

## 5. 无危害（None）

| # | 判定条件 |
|---|----------|
| N1 | 只反序列化 **服务端签发且 HMAC/签名校验** 的数据，密钥不泄露 |
| N2 | 使用安全 API（`json.loads`、`yaml.safe_load`、Jackson 无多态） |
| N3 | 数据完全来自可信内部服务且通道完整受控（需谨慎论证） |
| N4 | 库「理论上支持」反序列化但项目 **从未调用** |

---

## 6. 白盒 / 黑盒证据要点

| | 白盒 | 黑盒 |
|--|------|------|
| 最低 | 用户输入 → `readObject`/`unserialize`/`pickle.loads` | 提交 payload 触发异常特征/gadget 行为 |
| Critical | 无签名 + 危险类型 | 命令执行证据 |
| none | `safe_load` / 类型白名单 | 接口不接受序列化 blob |
