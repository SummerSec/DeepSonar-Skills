# 全局严重度等级定义

本文件定义四个等级的 **通用含义**。具体到某一漏洞类型时，以 `references/<type>.md` 的细则为准；细则与本文件冲突时，**以类型细则为准**。

---

## 1. 严重（Critical）

### 定义

在 **现实可达到的攻击前提** 下，攻击者能造成下列 **任一** 沦陷级后果：

- **远程代码执行（RCE）** 或等价完全主机/容器控制  
- **核心数据平面沦陷**：整库读写、全盘敏感文件读写、密钥托管系统被掏空  
- **身份平面沦陷**：未认证或低权限即可伪造任意用户/管理员，或批量账户接管  
- **租户/多租户隔离崩溃**：跨租户读写或管理他人全部数据  
- **云/基础设施接管**：通过 SSRF/密钥等拿到可创建资源、读全量密钥的云凭证  

### 共性特征

| 维度 | 要求 |
|------|------|
| 利用前提 | 通常为 **未认证** 或 **普通低权限用户**；无需稀有管理员权限 |
| 影响面 | 系统级 / 租户级 / 全体用户级，而非单个次要对象 |
| 可利用性 | 路径清晰，无需不现实的前置（如已是 root、已持有域管） |
| 证据 | 白盒有完整 source→sink；黑盒有可复现请求或等价旁证 |

### 不是严重的情况（常见误判）

- 需要 **已是管理员** 才能触发的 RCE（通常最多高危，视暴露面定）  
- 仅内网、且无跳板路径的「理论 RCE」  
- 影响仅限攻击者自己的数据  

---

## 2. 高危（High）

### 定义

可现实利用，造成 **重大安全后果**，但尚未满足「一键系统级沦陷」的严重标准，例如：

- 大量敏感个人数据 / 业务机密 **泄露或篡改**（范围大，但非整库一键）  
- **权限提升到管理功能**，或可操作高价值对象（资金、权限、配置）  
- 明确的 **利用链前半段**，在当前环境下再走 1 步即可到 Critical（如 SSRF 到 metadata 但尚未证明出凭证）  
- 生产级密钥/Token **有效且可滥用**，影响面大但限定某一子系统  
- 认证绕过影响重要功能，但未到「任意用户完全接管」  

### 共性特征

| 维度 | 要求 |
|------|------|
| 利用前提 | 远程可触达；可为普通用户或特定角色 |
| 影响面 | 重大业务/数据/权限，短时间内可造成事故 |
| 可利用性 | 有稳定复现或高置信代码路径 |
| 与严重分界 | 未证明「全系统/全租户/任意身份」级后果时，落在高危 |

---

## 3. 中危（Medium）

### 定义

存在真实安全弱点，但 **单独利用** 时后果有限，或利用条件明显受限：

- 仅影响 **少量非核心数据** 或单个低价值对象  
- 需要 **较强前提**（特定配置、已持有半吊子权限、复杂竞态且难稳定）  
- 有注入/越权迹象，但 **只能读到非敏感字段** 或攻击者本可合法看到的数据  
- 防护 partial bypass，尚不能稳定造成重大影响  
- 依赖其它未证明漏洞才能升级  

### 本仓处理

- **必须会定级为 medium**（语义完整）  
- **默认不写入正式 findings / 不建议自动 verify**  
- 可在进度文件记：`downgraded: medium — 原因`

---

## 4. 无危害（None）

### 定义

下列情况 **不构成** 应修复的安全漏洞（或不是安全问题）：

| 类别 | 示例 |
|------|------|
| 不可达 | 死代码、未挂载路由（预发 / DEV / 灰度环境按 ADJ-E1–E3 判定，不一律 none） |
| 已有效防护 | 参数化查询、严格白名单、框架自动编码且无绕过 |
| 无攻击者控制 | 输入完全来自服务端常量/可信服务 |
| 纯质量/体验 | 缺注释、慢查询、UI 问题 |
| 信息性 | 版本号、无敏感 stack、public 配置 |
| 误报 | 扫描器匹配字符串但语义不是漏洞 |
| 授权外/不可测 | 前提不现实（需物理接触、已是 hypervisor 管理员） |
| 假密钥 | 文档示例、明确 `test`/`dummy`、已验证失效 |

### 本仓处理

- 定级 `none`，**不报告**  
- 不要写成「建议修复的中低危」来凑数

## 5. 定级辅助：前提 × 影响 矩阵（通用）

| 影响 ↓ \ 前提 → | 未认证 / 匿名 | 普通登录用户 | 管理员 / 高权限 |
|-----------------|---------------|--------------|-----------------|
| 任意 RCE / 整库 / 任意用户接管 | **严重** | **严重** | 高危（若管理面仅内网可再降，需论证） |
| 大量敏感数据读写 / 管理功能越权 | **严重或高危** | **高危** | 中危～高危（看是否预期能力） |
| 少量敏感或单对象越权 | 高危 | 中危～高危 | 中危或无危害（若符合管理员职责） |
| 非敏感信息 / 理论问题 | 中危或无危害 | 无危害 | 无危害 |

> 「管理员可做的运维能力」本身不是漏洞；**未授权的人获得了不该有的能力** 才是漏洞。
>
> **执行位置不参与定档**：同一缺陷发生在服务端、CI 扫描节点、开发者本机（CLI / 桌面端 / IDE 插件）时，档位差异只来自**攻击前提**（是否需要提交工件的入口、是否需要受害者主动操作）与**凭证面**（节点持有 git 凭证 / 平台 token / 云密钥）；不得因为「不在服务端」直接判 `none`，也不得因为「在客户端」自动降档。
>
> **受限管理角色**（有管理角色但对目标资源无权限）不直接落「管理员 / 高权限」列：按「是否取得该角色之外的额外能力」判定，成立则按对应影响与「普通用户」列取档（如店铺管理员→邮件模板 SSTI 归 `rce.md`），不成立则不报。

## 6. 白盒 vs 黑盒在定级上的差异

| | 白盒 | 黑盒 |
|--|------|------|
| 证据 | source→sink、中间防护、部署入口 | 请求序列、响应差异、OOB、状态变化 |
| 可升严重 | 代码证明未认证入口直达 RCE sink | 实际打出 shell / 读到 /etc/shadow 或 metadata 凭证 |
| 易误判 | 「有危险 API」但输入不可控 → **none** | 「报错像注入」但无数据外带 → **none/medium** |
| 降级 | 有 auth 中间件且无法绕过 | WAF 稳定阻断且无绕过证据 |

**同一漏洞**：白盒与黑盒应使用 **同一套等级定义**；证据形式不同，等级标准相同。

## 7. 数据规模 × 字段敏感度（量化门槛）

「大量敏感个人数据」必须落到本矩阵才能定档。先按字段定敏感度，再按规模取档；**矩阵与类型细则取较高者**。

**前置条件（不满足则不进矩阵）**：缺陷必须已成立 **越权 / 未授权访问 / 非公开数据泄露**。「设计上公开」的数据（公开资料、公开 API、已对外披露内容）按 `authz.md#N1` 与 §4 记 `none`，**不因数量大抬档**；低敏列仅在越权成立且非公开时适用。

| 规模 \ 字段 | 低敏 | 中敏 | 高敏 |
|-------------|------|------|------|
| 单条 / 少量 | none | medium | medium–high |
| 批量可枚举（百~千级） | medium | high | high |
| 全站可遍历 / 万级以上 | medium–high | high | **critical** |

| 字段敏感度 | 判定条件 |
|------------|----------|
| 低敏 | 昵称、公开内容、已对外披露的信息（**设计上公开者走 `none`**） |
| 中敏 | 订单、日志、内部配置、非公开业务数据 |
| 高敏 | 身份证、银行卡、手机号 + 真实姓名、健康、金融画像、私密会话 |

| 规模值 | 判定条件 |
|--------|----------|
| `single` | 单条或少量记录，需逐条指定 |
| `enumerable` | 可通过遍历 / 枚举批量获取（百~千级） |
| `full_dump` | 全站可遍历、单接口万级以上、全量用户级 |

- 三条必填字段：`data_scale`、`data_sensitivity`，以及环境字段 `environment`（见 `shared/finding-schema.md`）
- 「可遍历所有机构」「单接口万级记录」「全量用户 PII」须落到 `full_dump` + 高敏 → `critical`
- 低敏数据到 `full_dump` 只在能证明 **规模本身** 带来额外影响（如批量关联还原身份）时取 `high`，否则取 `medium`
- 矩阵只约束 **数据面** 缺陷；代码执行、身份伪造等按类型细则定档

## 8. 调整条款（ADJ，命中即按本条处理）

### 8.1 环境

| # | 判定条件 |
|---|----------|
| ADJ-E1 | 预发 / 灰度 / DEV 环境与生产 **同构**（同数据源、同鉴权链路、同代码分支）→ **按生产定档**，evidence 标注环境即可 |
| ADJ-E2 | 仅 mock 数据，或鉴权链路与生产不同 → **降一档** |
| ADJ-E3 | 仅本地开发环境、无公网可达 → `none` |

### 8.2 修复绕过与复报

| # | 判定条件 |
|---|----------|
| ADJ-B1 | **修复绕过**（bypass of prior fix）：以绕过后的实际影响重新定档，**不得**沿用原报告档位；`severity_rule` 填本次命中的条款，finding 另填 `regression_of` |
| ADJ-B2 | 同一根因的多次复报**合并为一条** finding，用 `related_findings` 记录其余报告（完全重复填 `duplicate_of`） |

### 8.3 链路终态

| # | 判定条件 |
|---|----------|
| ADJ-C1 | 链路定档取 **链路终态可达的最高档**；仅在终态未证实时，才落到「利用链前半段 → high」 |
| ADJ-C2 | **跨根因打包**：每个根因一条 finding，`severity` 各自独立（允许一条 critical + 一条 medium），用 `related_findings` 互相引用 |

> ADJ 条款只调整定档，不改变「本仓默认只报 C/H」；是否需要输出 medium/low 见 `shared/severity-policy.md` 的 `report_policy` 开关。
